# VK Currency Bot

Бот для сообщества ВКонтакте, который предоставляет актуальные курсы валют Центрального Банка РФ и поддерживает диалог с
пользователем с помощью локальной нейросети (Ollama).

🔗 **[Ссылка на работающего бота (сообщество ВК)](https://vk.ru/club242331435)**
*(Для тестирования необходимо вступить в сообщество и написать любое сообщение в личные сообщения группы).*

## 🚀 Возможности

- Получение курсов валют (USD, EUR, CNY и др.) по данным ЦБ РФ.
- Поддержка синонимов (доллар, бакс, usd).
- Кэширование списка валют для снижения нагрузки на API ЦБ.
- Ведение истории запросов (вывод последних 5 запросов по слову `история`).
- Интеграция с локальной LLM (Ollama) для ответов на вопросы не по теме.
- Отказоустойчивость: при сбоях ВК/ЦБ бот отвечает заглушкой, а не падает.
- Автоматическая очистка БД: история запросов старше 10 дней удаляется по расписанию.

## 🛠 Технологический стек

- **Java 17**
- **Spring Boot 3** (Web, Data JPA, Actuator, Validation, Retry)
- **PostgreSQL** + **Flyway** (миграции)
- **Hibernate** (ORM)
- **Caffeine Cache** (кэширование в памяти)
- **Jackson** (JSON для ВК/Ollama, XML для ЦБ)
- **Lombok**
- **Ollama** (локальная LLM, модель `qwen2.5:7b`)
- **Maven**

## 🏗 Архитектурные решения

1. **Два HTTP-клиента (`RestClient`):**
    - Быстрый (10 сек) для ВК API и ЦБ — чтобы сетевой сбой не вешал пул потоков.
    - Долгий (40 сек) для Ollama — так как локальная LLM отвечает медленно.
    - Асинхронность через пул потоков не дает долгому ответу ИИ блокировать остальных пользователей.
2. **Кэширование (Caffeine):** Кэшируем весь список валют целиком на 12 часов — один сетевой запрос вместо запроса на
   каждое сообщение. Поиск по списку O(n), но n=44, так что это дешевле любого сетевого вызова.
3. **Иммутабельные конфиги:** Настройки вынесены в `@ConfigurationProperties` с валидацией и `final` полями (Fail-Fast
   при старте, если нет токена).
4. **Обработка ошибок:** Настроены механизмы `@Retryable` для повторных попыток при сетевых сбоях и `@Recover` для
   Graceful Degradation (бот не падает, а отвечает заглушкой).
5. **Плановая очистка данных (`@Scheduled`):** История запросов не хранится вечно.
   Настроен шедуллер, который каждую ночь удаляет записи старше 30 дней. Это защищает БД и диск VPS от бесконечного
   роста.

## 💬 Пример работы

- **Пользователь:** `курс доллара`
- **Бот:** `Доллар на сегодня оценивается в 80.56 рублей. Ещё что-нибудь?`
- **Пользователь:** `Анекдот`
- **Бот:** `Конечно, расскажу анекдот... (Чтобы вернуться к курсам, просто напиши название валюты одним словом)`

## 🚦 Как запустить локально

1. Клонируйте репозиторий.
2. Создайте базу данных PostgreSQL `vk_bot_db`.
3. Создайте файл `env.properties` в корне проекта. Он подхватывается автоматически через
   `spring.config.import=optional:file:env.properties`. Заполните его:
   ```properties
   VK_GROUP_ID=ваш_id
   VK_ACCESS_TOKEN=ваш_токен
   DB_URL=jdbc:postgresql://localhost:5432/vk_bot_db
   DB_USERNAME=ваш_логин
   DB_PASSWORD=ваш_пароль
   AI_URL=http://localhost:11434/api/generate
   AI_MODEL=qwen2.5:7b
   ```
4. Запустите локально Ollama.
5. Запустите приложение `mvn spring-boot:run`.

## ☁️ Развертывание (Production)

Проект развернут на облачной платформе **Render**. Render автоматически собирает проект из GitHub (на основе
`Dockerfile` в репозитории).

**Почему Render, а не VPS?**
Изначально планировался VPS с нативным запуском (systemd) для экономии памяти. Однако для пет-проекта Render оказался
удобнее: бесплатный хостинг и авто-деплой из GitHub.

**Проблема засыпания и ее решение:**
Бесплатный тариф Render усыпляет контейнер через 15 минут без входящего трафика. Чтобы бот не засыпал днем, настроен
внешний пингер (**cron-job.org**), который стучится в `/actuator/health` каждые 10 минут. В ночное время (01:00–07:00)
пинги отключены для экономии бесплатных часов.

**Ограничения:**
Из-за засыпания, в ночные часы, сообщения, отправленные в это время, теряются (потому что `ts` LongPoll хранится в
памяти). Для
пет-проекта это допустимо. В продакшене это решается переносом `ts` в БД, Redis или переездом на брокер сообщений (
Kafka).

## ⚠️ Ограничения (осознанные)

- **`ts` Long Poll хранится в памяти:** при рестарте приложения сообщения, пришедшие за время простоя, теряются. Для
  пет-проекта допустимо. Для продакшена необходимо внедрение inbox-паттерна в PostgreSQL или использование брокера
  сообщений (Kafka).
- **Один инстанс:** сейчас приложение работает в одном инстансе. Для горизонтального масштабирования потребуется переход
  с Long Poll на Callback API и внедрение распределённых блокировок (Redis Lock) или очередей (Kafka), чтобы избежать
  дублирования обработки сообщений. Сейчас в этом нет необходимости из-за низкой нагрузки.
